## 💡 Архитектура решения

Решение задачи — извлечение коллокаций из статей Википедии с использованием метрики **NPMI** (Normalized Pointwise Mutual Information). Задача решается полностью на **DataFrame API** с использованием оконных функций, множественных join'ов и агрегаций.

### 🔹 Общая идея алгоритма

Алгоритм состоит из **6 последовательных этапов**:

1. **Парсинг и очистка** — извлечение слов из статей, нормализация, удаление стоп-слов
2. **Подсчёт частот слов** — для вычисления $P(a)$ и $P(b)$
3. **Формирование биграмм** — через оконную функцию `lead()` внутри каждой статьи
4. **Подсчёт частот биграмм** — для вычисления $P(ab)$
5. **Вычисление NPMI** — через два join с таблицей частот слов
6. **Фильтрация и сортировка** — отбор топ-39 коллокаций

---

### 🔹 Этап 1: Парсинг и очистка текста

**Чтение входных данных:**
- Стоп-слова читаются как текстовый файл с переименованием колонки value → stop
- Статьи читаются через read.csv с явной схемой (две колонки: id и text, разделитель — табуляция)
- Явная схема нужна, так как файлы в HDFS не имеют заголовков

**Разбиение на слова и нормализация:**
- lower(col("text")) — приводим весь текст к нижнему регистру
- split(..., " ") — разбиваем текст по пробелам в массив слов
- posexplode — ключевая функция: в отличие от обычного explode, она возвращает позицию элемента в массиве (pos) вместе со значением (word). Это критично для формирования биграмм — нужно знать порядок слов внутри статьи

**Очистка слов:**

- regexp_replace(col("word"), r"^\W+|\W+$", "") — удаляет все не-латинские символы в начале и конце каждого слова (согласно условию задачи)

**Фильтрация и удаление стоп-слов:**

- filter(col("word") != "") — убираем пустые строки (после regexp_replace слово может стать пустым)
- filter(col("word").rlike("^[a-z]+$")) — оставляем только слова из латинских букв в нижнем регистре
- left_anti join со стоп-словами — элегантная замена NOT IN: оставляет только те слова, которых нет в списке стоп-слов
- cache() — кэшируем результат, так как valid_words_df используется далее дважды (подсчёт общего числа слов + формирование биграмм)


### 🔹 Этап 2: Подсчёт частот слов

- total_words_count — общее количество слов до фильтрации биграмм (по условию задачи)
- word_counts_df — таблица частот каждого слова: (word, word_count)
- cache() — кэшируем, так как эта таблица будет join'иться дважды (для первого и второго слова биграммы)

### 🔹 Этап 3: Формирование биграмм

Разбор оконной функции:
- Window.partitionBy("id").orderBy("pos") — окно разбивается по статьям (id) и упорядочивается по позиции слова (pos)
- lead("word").over(window_spec) — для каждого слова берёт следующее слово в том же окне (той же статье). Если слова нет (конец статьи) — возвращает NULL
- filter(col("next_word").isNotNull()) — убираем последнее слово каждой статьи (у него нет пары)
- concat_ws("_", col("word"), col("next_word")) — объединяем два слова через _ в биграмму

Почему partitionBy("id")? Биграммы должны формироваться только внутри одной статьи. Слово в конце одной статьи и слово в начале следующей — не биграмма.

cache() — биграммы используются дважды: для подсчёта total_pairs_count и для группировки частот.

### 🔹 Этап 4: Подсчёт частот биграмм

- total_pairs_count — общее количество биграмм до фильтрации по 500 (по условию задачи)
- bigram_counts_df — таблица частот каждой биграммы
- filter(col("count") >= 500) — оставляем только биграммы, встретившиеся не реже 500 раз. NPMI считается только для них, но общие счётчики (total_words_count, total_pairs_count) включают все биграммы

### 🔹 Этап 5: Вычисление NPMI
Подготовка к join:

- Разбиваем биграмму обратно на два слова через split + getItem — нужно для join с таблицей частот слов

Первый join — частота первого слова:

- Переименовываем word → w1_join чтобы избежать конфликта имён колонок
- left join — на случай если слово не встретилось (хотя после фильтрации это маловероятно)
- Переименовываем word_count → count_w1

Второй join — частота второго слова:

- Аналогично первому join, но для второго слова биграммы

Вычисление NPMI:

- P_ab = count / total_pairs_count — вероятность биграммы
- P_a = count_w1 / total_words_count — вероятность первого слова
- P_b = count_w2 / total_words_count — вероятность второго слова
- PMI = ln(P_ab / (P_a * P_b)) — точечная взаимная информация
- NPMI = -PMI / ln(P_ab) — нормализованная PMI в диапазоне [-1, 1]
Важно: total_words_count и total_pairs_count подставляются как литералы (lit(...)) — это скалярные значения, вычисленные заранее через .count().

### 🔹 Этап 6: Финальная сортировка и вывод

- orderBy(col("NPMI").desc(), col("bigram")) — сортировка по убыванию NPMI, при равенстве — лексикографически по биграмме
- limit(39) — берём топ-39 коллокаций
- collect() — действие, запускающее все вычисления и возвращающее результат на драйвер
Выводим только биграммы, без значений NPMI (по условию задачи)

## 📊 Ключевые оптимизации

| Оптимизация | Где применена | Эффект |
|-----------|------------------------|------------------------|
| cache() | valid_words_df, word_counts_df, bigrams_df | Избегает повторного вычисления при множественном использовании |
| left_anti join | Удаление стоп-слов | Одна операция вместо filter + NOT IN |
| lead() оконная функция | Формирование биграмм | Избегает self-join, работает за один проход |
| partitionBy("id") | Оконная функция | Биграммы не "перетекают" между статьями |
| posexplode | Разбиение на слова | Сохраняет позицию для корректного формирования биграмм |
| Фильтрация до NPMI | count >= 500 | Снижает объём данных для дорогостоящих join'ов |

Почему именно DataFrame API?

1. Catalyst Optimizer автоматически оптимизирует план выполнения: объединяет проекции, устраняет избыточные shuffle, применяет predicate pushdown
2. Оконные функции (lead() OVER) — декларативный способ формирования биграмм без ручного управления партициями
3. left_anti join — встроенная операция для фильтрации, которую в RDD пришлось бы реализовать через leftOuterJoin + filter(None)
4. Читаемость — код описывает что нужно сделать, а не как — каждый этап соответствует математической формуле

## 🔹 Важные детали реализации

Порядок операций критичен:
1. Сначала считаем total_words_count и total_pairs_count — до фильтрации биграмм по 500
2. Фильтруем биграммы по 500 — после подсчёта общих счётчиков
3. Считаем NPMI только для отфильтрованных биграмм

Почему posexplode, а не explode?
- explode возвращает только значения — теряется информация о позиции
- posexplode возвращает (позиция, значение) — это позволяет через lead() найти следующее слово в той же статье
- Без позиции биграммы формировались бы между последним словом одной статьи и первым словом следующей

Почему два отдельных join, а не один?
- DataFrame API не поддерживает join по нескольким ключам с разными таблицами в одной операции
- Каждый join добавляет одну колонку (count_w1, count_w2)
- Catalyst Optimizer может объединить эти join'ы при генерации плана выполнения
