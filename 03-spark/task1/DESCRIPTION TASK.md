## 💡 Архитектура решения

Решение задачи — поиск кратчайшего пути между вершинами **12** и **34** в ориентированном графе Twitter — реализовано двумя способами: через **RDD API** и **DataFrame API**. В обоих случаях используется итеративный **BFS (поиск в ширину)** с сохранением пути для каждой вершины.

### 🔹 Общая идея алгоритма

BFS в распределённой среде реализуется через **итерации**:

1. **Инициализация**: начинаем с вершины `start = 12`, путь = `[12]`
2. **На каждой итерации**:
   - Берём текущую "фронтальную границу" (`frontier`) — вершины, достигнутые на предыдущем шаге
   - Делаем **join** с рёбрами графа → получаем кандидатов на следующий уровень
   - Фильтруем уже посещённые вершины (`visited`)
   - Проверяем, достигли ли целевой вершины `target = 34`
   - Если нет — добавляем новые вершины в `visited` и повторяем
3. **Остановка**: когда найден `target` или `frontier` пуст (путь не существует)

**Ключевая особенность**: вместо хранения только расстояния, храним **полный путь** (`[12, 42, 57, 34]`), чтобы в конце вывести последовательность вершин.

## 🔹 Реализация на RDD API (`task1_rdd.py`)

**Парсинг и подготовка рёбер:**
- parse_edge разворачивает ребро: исходно файл хранит user → follower, но для обхода от start к target нужно идти в обратном направлении, поэтому возвращаем (follower, user)
- partitionBy(100) — явное партиционирование по ключу (вершине), чтобы join'ы были эффективнее (меньше shuffle)
- persist() — кэширование RDD в памяти, так как edges используется на каждой итерации

**Инициализация BFS:**
- frontier — RDD пар (вершина, путь), содержит только вершины текущего уровня BFS
- visited — RDD пар (вершина, 1), множество всех посещённых вершин (нужно для исключения циклов)

**Основная итерация:**
- frontier.join(edges) — для каждой вершины из frontier находим все исходящие рёбра
- map — формируем кандидатов: ключ = следующая вершина, значение = путь + новая вершина

**Фильтрация посещённых:**
- leftOuterJoin с visited — для каждого кандидата проверяем, был ли он уже посещён
- filter(lambda x: x[1][1] is None) — оставляем только тех, кого не было в visited (правая часть join = None)
- Это исключает циклы и повторную обработку вершин

**Проверка достижения цели:**

- take(1) — действие (action), которое запускает вычисления и возвращает первый найденный путь
- Если found_vertex не пуст — путь найден, выходим из цикла

**Обновление visited:**

- union — добавляем новые вершины к множеству посещённых
- unpersist() — освобождаем память от старых RDD (критично для итеративных алгоритмов!)
- frontier = new_frontier — переходим к следующему уровню BFS



## 🔹 Реализация на DataFrame API (task1_df.py)

**Парсинг и подготовка рёбер:**

- read.text — читает файл как текстовый DataFrame с одной колонкой value
- split(value, '\t') — разбивает строку по табуляции
- cast(... as int) — преобразует строки в целые числа
- Колонки переименованы: src = источник ребра, dst = цель (разворот для обхода от start)
- repartition(100).cache() — аналог partitionBy + persist в RDD

**Инициализация BFS:**

- frontier — DataFrame с колонками id (вершина) и path (список вершин пути)
- visited — DataFrame с одной колонкой id (посещённые вершины)

**Основная итерация:**

- join по условию frontier.id == edges.src — находим рёбра из текущей границы
- concat(col("path"), array(col("dst"))) — добавляем новую вершину в путь (аналог path + [new_vertex] в RDD)
- frontier.unpersist() — освобождаем память сразу после использования

**Фильтрация посещённых через left_anti join:**

- left_anti join — элегантная замена leftOuterJoin + filter(None) из RDD версии
- Возвращает только строки из candidates, которых нет в visited
- Одна операция вместо двух — чище и быстрее

**Проверка достижения цели:**

- filter + limit(1).collect() — аналог filter + take(1) в RDD
- collect() — действие, запускающее вычисления и возвращающее результат на драйвер

**Обновление visited:**

- union + distinct — добавляем новые вершины и убираем дубликаты
- В RDD версии дубликаты не возникали благодаря leftOuterJoin, здесь нужна явная distinct()

## 📊 Сравнение производительности

- DataFrame API быстрее на ~33% благодаря Catalyst Optimizer и Tungsten
- Код DataFrame короче и читаемее — особенно заметна замена leftOuterJoin + filter(None) на left_anti join
- RDD даёт больше контроля над партиционированием (partitionBy по ключу) и типами данных
- В обоих случаях критично важно управление памятью через persist()/cache() и unpersist() — без этого итеративный BFS быстро съест всю память кластера

🔹 Почему DataFrame быстрее?
1. Catalyst Optimizer — автоматически переписывает план выполнения, объединяет операции, устраняет избыточные shuffle
2. Tungsten — эффективное хранение данных в памяти (off-heap), генерация байт-кода вместо интерпретации Python
3. left_anti join — одна оптимизированная операция вместо двух (leftOuterJoin + filter)
4. Columnar storage — данные хранятся в колоночном формате, что ускоряет операции над отдельными колонками

🔹 Когда RDD всё же полезен?
- Нужен полный контроль над партиционированием (partitionBy по конкретному ключу)
- Работа с кастомными типами данных, не поддерживаемыми в DataFrame
- Сложные графовые алгоритмы с нестандартной логикой обхода
- Когда требуется максимальная гибкость в обработке каждой записи
