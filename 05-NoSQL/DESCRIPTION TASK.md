## 🛠 Стек технологий

- **Apache HBase 1.2.0** (Cloudera CDH) — распределённое column-family хранилище
- **Apache Spark 2.4.0** (PySpark) — распределённая обработка и предагрегация данных
- **HappyBase** — Python-библиотека для взаимодействия с HBase Thrift API
- **Apache Hadoop 2.6.0** (HDFS) — источник сырых данных (`/data/hobod/pubg`)
- **Python 3** — язык реализации клиентской логики и Spark-джобы
- **Bash** — скрипты автоматизации запуска

## 💡 Архитектура решения

Решение построено на принципе **Write-Heavy, Read-Optimized**. Основная вычислительная нагрузка (фильтрация, группировка, подсчёт) перенесена на этап записи (Writer), чтобы обеспечить молниеносное чтение (Reader).

### 🔹 1. Проектирование модели данных (HBase Schema)

В отличие от реляционных СУБД, в HBase критически важен выбор **Row Key**. 

| Компонент | Значение | Обоснование |
|-----------|----------|-------------|
| **Table Name** | `pubg_kills_bessmertnyjde` | Изоляция данных пользователя |
| **Column Family** | `weapons` | Группировка данных об убийствах. Настроено сжатие `SNAPPY` и `ROW` Bloom Filter для ускорения точечных чтений. |
| **Row Key** | `{match_id}_{time_bucket}` | Композитный ключ. Позволяет делать точечные чтения (`get`) для конкретного матча и временного интервала, избегая полного сканирования таблицы. |
| **Column Qualifier** | `{weapon_name}` (напр. `weapons:AKM`) | Динамические колонки. Тип оружия становится именем колонки, что идеально ложится на модель wide-column. |
| **Value** | `{kill_count}` (строка) | Количество убийств данным оружием в данном бакете времени. |

**Пример строки в HBase:**
- **Row Key**: `abc123match_200` (матч abc123, интервал 200-299 сек)
- **Column**: `weapons:Kar98k` → **Value**: `15`
- **Column**: `weapons:AKM` → **Value**: `42`

### 🔹 2. Writer: Предагрегация и загрузка (`writer.py`)

Прямая запись сырых логов в HBase неэффективна. Используется двухэтапный подход:

1. **Spark-агрегация**:
   - Чтение CSV из HDFS.
   - Фильтрация `null` значений.
   - **Бакетирование времени**: `time_bucket = (floor(time / 100) * 100)`. Время округляется вниз до ближайшей сотни секунд. Это снижает гранулярность данных и уменьшает количество строк в HBase, сохраняя возможность фильтрации по диапазону.
   - **Группировка**: `groupBy("match_id", "time_bucket", "killed_by").count()`. Мы считаем убийства *до* записи в HBase.

2. **Пакетная запись (Batching)**:
   - Использование `happybase` с `batch_size=5000`.
   - Данные отправляются в HBase пачками, что минимизирует сетевые задержки и нагрузку на RegionServer.

### 🔹 3. Reader: Оптимизированное чтение (`reader.py`)

Reader поддерживает два режима работы, кардинально различающихся по производительности:

**Режим А: Запрос по конкретному матчу (`--match`)**
- **Алгоритм**: Цикл по нужным `time_bucket` в диапазоне `[start, end]`.
- **Операция HBase**: `table.row(row_key)` (точечное чтение / Point Lookup).
- **Сложность**: $O(K)$, где $K$ — количество временных бакетов в диапазоне. Чрезвычайно быстро, не нагружает кластер.

**Режим Б: Запрос по всем матчам (без `--match`)**
- **Алгоритм**: Полное сканирование таблицы (`table.scan()`).
- **Фильтрация**: Парсинг `row_key` на клиенте (`extract_match_and_bucket`). Если `bucket` попадает в диапазон `[start_bucket, end_bucket]`, данные агрегируются в `defaultdict` на стороне Python.
- **Оптимизация**: Вывод прогресса каждые 10 000 просканированных строк для мониторинга.

**Финальная сортировка**: 
Результаты сортируются по убыванию количества убийств (`-x[1]`), а при равенстве — лексикографически по названию оружия (`x[0]`), что обеспечивает детерминированный вывод.
