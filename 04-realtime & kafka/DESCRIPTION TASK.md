## 💡 Архитектура решения

### 🔹 Задача 1: Сегментация с HyperLogLog (Эмуляция потока)

**Подход:**
Поскольку реальный поток данных в задаче эмулируется, используется `ssc.queueStream`, который по очереди выдаёт RDD из заранее подготовленного списка файлов HDFS (`/data/course4/uid_ua_100k_splitted_by_5k`).

**Ключевые оптимизации:**
1. **Локальная агрегация (`mapPartitions`):** Вместо добавления каждого `uid` в глобальный HyperLogLog (что потребовало бы дорогостоящих сетевых пересылок), мы создаём локальный HLL для каждой партиции, заполняем его и затем объединяем (`update`) в глобальный словарь `hll_state` на драйвере.
2. **Эвристика:** Простая и быстрая проверка через `in` после приведения User-Agent к нижнему регистру (`ua_lower`), что избегает тяжёлых регулярных выражений или внешних библиотек парсинга.

### 🔹 Задача 2: Подсчёт сообщений в Kafka
**Подход:**
Используется утилита `kafka-console-consumer.sh` с флагом `--from-beginning` и ограничением по времени `--timeout-ms 60000`. Скрипт на Python оборачивает этот вызов через `subprocess.Popen` и считает количество непустых строк в `stdout`.
**Важно:** Ошибка `kafka.consumer.ConsumerTimeoutException` в логах является ожидаемым поведением для старого API потребителя при достижении таймаута. Скрипт корректно перехватывает её и выводит итоговый счётчик.

### 🔹 Задача 3: Kafka Producer (Эмуляция потока)
**Подход:**
Скрипт читает файлы из HDFS по одному. Внутри каждого файла строки отправляются в топик через `producer.send()`. После отправки файла вызывается `producer.flush()` (гарантия доставки) и `time.sleep(10)`, что создаёт реалистичную нагрузку и эмулирует приход новых микробатчей данных каждые 10 секунд.

### 🔹 Задача 4: Spark Streaming Consumer (Direct Stream)
**Подход:**
Используется `KafkaUtils.createDirectStream`.

**Почему Direct Stream, а не Receiver?**
- Эффективность: Не требует Write-Ahead Logs (WAL) и отдельного executors для получения данных.
- Exactly-once семантика: Смещения (offsets) управляются самим Spark, а не Zookeeper, что позволяет гарантировать обработку каждого сообщения ровно один раз.
- Параллелизм: Количество партиций RDD напрямую соответствует количеству партиций Kafka.

Логика обработки (`process_rdd`) идентична Задаче 1, но применяется к потоку `(key, value)`, где `value` содержит строку `uid \t user_agent`.

### 🔹 Задача 5: Управление Offset'ами и Партициями
**Подход:**
Использование `argparse` для приёма параметров `--partition`, `--offset-from`, `--offset-to`.

## 💡 Ключевые инсайты
1. HyperLogLog vs `countDistinct`: При работе с потоковыми данными точный подсчёт уникальных пользователей (`distinct`) требует перемешивания (shuffle) всех данных по сети, что убивает производительность. HyperLogLog с `error_rate=0.01` использует фиксированный объём памяти (~1.5 КБ на сегмент) и работает за O(1), жертвуя лишь 1% точности ради скорости.
2. Ограничения Kafka 0.8 API: Современные приложения используют Kafka 0.10+ API (`createDirectStream` с параметром `startingOffsets`), который позволяет гибко управлять чтением без указания конкретной партиции. В данной задаче мы работаем с legacy-пакетом (`2.3.0`), что требует обходных путей (как фильтрация по `offsetRanges`).
3. State Management: В задачах 1, 4 и 5 состояние (`hll_state`) хранится в памяти драйвера. Для долгоживущих production-стримов это антипаттерн (риск потери состояния при падении драйвера). В реальных системах для этого используются `updateStateByKey` или внешние хранилища (Redis, HBase).
