## 🛠 Стек технологий

- **Apache Hive** (Cloudera CDH 5.11.2) на кластере МФТИ
- **Apache Hadoop HDFS** (хранение данных в `/data/hive/fns2` и `/user/hobod2026s001/`)
- **JsonSerDe** (`org.openx.data.jsonserde.JsonSerDe`) — десериализатор JSON-строк в колонки Hive
- **Форматы хранения:** TEXTFILE, ORC, Parquet
- **YARN** (управление ресурсами кластера)
- **Bash** (скрипт запуска `run.sh`)

## 💡 Архитектура решения

Решение задачи состоит из создания трёх таблиц с одинаковой структурой, но разными форматами хранения (Text, ORC, Parquet), и сравнения скорости выполнения аналитического запроса на каждой из них.

### 🔹 Шаг 1: Создание таблицы в формате Text (`00_task2-create-table-text.sql`)

**Создание внешней таблицы:**
- Таблица содержит только необходимые для анализа поля (упрощённая структура по сравнению с исходной kkt_transactions)
- STORED AS TEXTFILE — стандартный текстовый формат, каждая строка хранится как есть
- Данные будут записаны в HDFS по пути /user/hobod2026s001/kkt_text

**Заполнение данными из исходной таблицы:**
- INSERT OVERWRITE — полностью перезаписывает данные в таблице (аналог CTAS, но с явным созданием схемы)
- Извлекаем нужные поля из вложенной структуры content исходной таблицы

### 🔹 Шаг 2: Создание таблицы в формате ORC (01_task2-create-table-orc.sql)
- ORC (Optimized Row Columnar) — колоночный формат хранения, оптимизированный для Hive
- Поддерживает сжатие, индексы и predicate pushdown
- Данные записываются в /user/hobod2026s001/kkt_orc

### 🔹 Шаг 3: Создание таблицы в формате Parquet (02_task2-create-table-parquet.sql)
- Parquet — колоночный формат хранения, разработанный совместно Twitter и Cloudera
- Эффективное сжатие и кодирование, поддержка вложенных структур
- Данные записываются в /user/hobod2026s001/kkt_parquet

### 🔹 Шаг 4: Аналитический запрос на каждой таблице
**Логика запроса:**
- Фильтруем только транзакции типа receipt (кассовые чеки)
- Группируем по userInn (налогоплательщик)
- Суммируем totalSum для каждого налогоплательщика
- Сортируем по убыванию прибыли
- Берём топ-1 (налогоплательщик с наибольшей прибылью)

### 📊 Результаты сравнения производительности

| Формат хранения данных | Время работы запроса |
|------------------------|----------------------|
| TEXT                   | 20850 msec           |
| ORC                    | 9140 msec            |
| Parquet                | 8720 msec            |

**Выводы:**
- **Parquet** показал наилучший результат (8720 мс) — колоночное хранение эффективно для агрегаций
- **ORC** занял второе место (9140 мс) — также колоночный формат, но немного медленнее Parquet в данном случае
- **TEXT** показал худший результат (20850 мс) — в 2.4 раза медленнее Parquet, так как требует полного сканирования строк

**Почему колоночные форматы быстрее?**
- При запросе `SUM(totalSum)` читаются только нужные колонки, а не вся строка целиком
- Лучшее сжатие данных → меньше I/O операций
- Predicate pushdown фильтрация происходит до чтения данных
- Векторизованное выполнение запросов

**Почему Parquet быстрее ORC в данном случае?**
- Parquet более эффективен для простых запросов с агрегацией
- Лучшая поддержка сжатия для числовых данных
- ORC может быть быстрее на более сложных запросах с множеством условий
