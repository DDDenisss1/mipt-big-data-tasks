## 🛠 Стек технологий

- **Apache Hive** (Cloudera CDH 5.11.2) на кластере МФТИ
- **Apache Hadoop HDFS** (хранение данных в формате Parquet)
- **Оконные функции Hive** (`SUM() OVER PARTITION BY ... ORDER BY ... ROWS UNBOUNDED PRECEDING`)
- **Формат хранения:** Parquet (таблица `kkt_transactions_parquet` из task2)
- **Bash** (скрипт запуска `run.sh`)

## 💡 Архитектура решения

Решение задачи — поиск налогоплательщиков, нарушающих п. 2 ст. 4.3 закона 54-ФЗ. Нарушение состоит в том, что транзакция "кассовый чек" (`receipt`) совершена в период, когда смена закрыта: между `closeShift` и следующим `openShift`, либо до первого `openShift`, либо после последнего `closeShift`.

Задача решается одним SQL-запросом с использованием **кумулятивных оконных функций** для отслеживания состояния смены в каждый момент времени.

### 🔹 Логика запроса (`00_task5_select.sql`)

Запрос состоит из четырёх уровней вложенности:

**Уровень 1 — Фильтрация и извлечение timestamp:**
- Оставляем только три типа транзакций, важных для анализа порядка смен
- Извлекаем unix-timestamp в секундах для корректного упорядочивания по времени
- kktregid — идентификатор конкретного ККТ (смена отслеживается отдельно для каждого ККТ)

**Уровень 2 — Вычисление кумулятивных счётчиков открытий и закрытий:**
Разбор оконных функций:
- PARTITION BY kktregid — счётчики считаются независимо для каждого ККТ, так как смены открываются и закрываются на конкретном устройстве
- ORDER BY ts — транзакции упорядочиваются по времени в хронологическом порядке
- ROWS UNBOUNDED PRECEDING — окно включает все строки от начала партиции до текущей (кумулятивная сумма)
- SUM(CASE WHEN subtype = 'openShift' THEN 1 ELSE 0 END) — кумулятивное количество открытий смен до текущей транзакции включительно
- SUM(CASE WHEN subtype = 'closeShift' THEN 1 ELSE 0 END) — кумулятивное количество закрытий смен до текущей транзакции включительно

Смысл счётчиков:
- open_count — сколько раз смена была открыта к моменту текущей транзакции
- close_count — сколько раз смена была закрыта к моменту текущей транзакции
- Если open_count > close_count → смена открыта (было больше открытий, чем закрытий)
- Если open_count = close_count → смена закрыта (каждое открытие было закрыто)
- Если open_count = 0 → смена ни разу не открывалась

**Уровень 3 — Фильтрация только чеков:**
- Оставляем только транзакции типа receipt — именно они являются потенциальными нарушениями
- Для каждого чека сохраняем состояние счётчиков на момент его совершения

**Уровень 4 — Определение нарушений:**

| Условие | Смысл |
|------------------------|----------------------|
| open_count = 0            | К моменту чека смена ни разу не открывалась — транзакция до первого openShift |
| close_count >= open_count | Количество закрытий больше или равно количеству открытий — смена закрыта, чек выдан между closeShift и следующим openShift, либо после последнего closeShift|

- DISTINCT userinn — каждый налогоплательщик-нарушитель выводится один раз, даже если у него несколько ККТ с нарушениями
- LIMIT 50 — ограничение вывода (требование условия для всех задач кроме 3-й)

---

🔹 Почему Parquet?
- Используется таблица kkt_transactions_parquet, созданная в task2, потому что:
- Parquet показал наилучшую производительность (8720 мс) при сравнении форматов
- Оконные функции требуют сортировки данных — колоночный формат ускоряет чтение нужных колонок (subtype, dateTime, userInn, kktRegId)
- Меньший объём данных на диске → быстрее передача по сети между нодами кластера

🔹 Обработка edge cases
- Несколько ККТ у одного налогоплательщика — PARTITION BY kktregid гарантирует независимый анализ каждого устройства; DISTINCT userinn объединяет результаты
- Несколько openShift подряд без closeShift — open_count > close_count, смена считается открытой, чеки легальны
- Несколько closeShift подряд без openShift — close_count > open_count, все последующие чеки считаются нарушениями
- NULL в dateTime — отфильтровываются на этапе CAST(regexp_extract(...)), так как regexp_extract вернёт пустую строку, CAST даст NULL, и сортировка поместит такие строки в начало (но они не влияют на корректность, так как subtype всё равно проверяется)
- Транзакции других типов (refund, correction и т.д.) — игнорируются через WHERE subtype IN (...)

🔹 Почему оконные функции, а не self-join?
- Оконные функции предпочтительнее self-join для этой задачи, потому что:
- Один проход по данным вместо многократного сканирования таблицы
- Естественное выражение кумулятивной логики — SUM() OVER ... ROWS UNBOUNDED PRECEDING прямо моделирует "счётчик событий до текущего момента"
- Меньше кода и выше читаемость по сравнению с коррелированными подзапросами
- Оптимизированное выполнение в Hive/Tez — оконные функции выполняются в рамках одного MapReduce-задания
